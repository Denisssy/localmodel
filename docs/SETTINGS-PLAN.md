# localmodel: настройки, `hub` и поток «ссылка с HF → рабочая модель»

План рефакторинга. Цель: любая настройка живёт в одном месте, видна с пояснением,
редактируется без ручного TOML, а модель с HuggingFace приезжает уже настроенной.

> **Статус.** Фазы 0–2 сделаны (2026-11-08/09). Фаза 0 — реестр `src/knobs.rs`.
> Фаза 1 — `src/resolve.rs` (provenance), `run --explain`, `--strict`,
> `settings --set/--unset/--show --origin`, `save()` на `toml_edit` (комментарии
> и ручной порядок переживают сохранение), разбор файла по таблицам и проверка
> `extra` по `llama-server --help`. Фаза 2 — `gguf::Meta` отдаёт KV-геометрию
> (attention-слои, головы, head_dim, SWA, nextn), `fit::for_gguf` считает VRAM,
> `fit::suggest_ctx` подбирает контекст. argv всех 6 моделей по-прежнему
> побайтово совпадает с эталоном. Дальше — фаза 3.

## 1. Что именно болит (по коду, не по ощущениям)

Плюс два бага, которые схема закрывает сама (мы их нашли на Ornith):

- `--cache-reuse 256` на гибридном SSM-контексте не поддерживается — llama.cpp пишет
  `cache_reuse is not supported ... disabled`. Это должно быть автоправилом, а не шумом.
- Draft-KV пришлось выражать через `extra`, потому что отдельного knob не было. Замер показал,
  что `q4_0` там не нужен вовсе — калькулятор VRAM это бы показал заранее.

## 2. Решение

**TUI не убирать. Убрать дублирование.** Проблема не в том, что интерфейс терминальный,
а в том, что *модель данных* плоская и размазана по коду. CLI-only слой оставит ту же
болезнь, только ещё менее обнаружимую.

Целевая архитектура — четыре слоя, каждый со своей ответственностью:

```
  knobs.rs       реестр: что можно настраивать (единственный источник правды)
      │
      ▼
  resolve.rs     Profile(defaults) ⊕ Profile(model) ⊕ CLI → Resolved + Source
      │
      ├──► build_args()  argv для llama-server (генерируется из реестра)
      ├──► fit.rs        калькулятор VRAM: GGUF + ctx + KV → fits/tight/no
      └──► hub.rs        экран: список моделей + отфильтрованные настройки + argv
```

`localmodel hub` — единственный интерактивный вход. `localmodel settings --set/--unset/--show`
— тот же реестр без TUI, для скриптов. Старый цепочечный `dialoguer`-редактор удаляется:
он третий по счёту дубль списка полей и худший по удобству (нет контекста, нет предпросмотра).

### Почему не ratatui

Рендер уже есть: `boxed()`, `section()`, цвета, скролл, raw-mode, panic-hook, `handle_key`
(`main.rs:2944-3233`). Для хаба нужны ровно те же примитивы: два списка, инлайн-ввод,
панель помощи. ratatui — это переписывание на виджеты, которых у нас нет, ради нуля
новых возможностей. Новых зависимостей не добавляем, кроме `toml_edit` (см. §7).

## 3. Слой 1: реестр настроек (`src/knobs.rs`)

Одна таблица. Из неё макросом генерируются `Profile`, `is_empty`, `overlay`, список строк UI,
парсер `--set`, и маппинг в argv.

```rust
pub struct Knob {
    pub key: &'static str,            // "ctx" — ключ в TOML и в --set
    pub label: &'static str,          // "context size"
    pub help: &'static str,           // одна строка под курсором
    pub long_help: Option<&'static str>, // по F1
    pub group: Group,                 // Context | Memory | Speed | Sampling | Server | Advanced
    pub kind: Kind,                   // Bool | Num{min,max,unit} | Enum(&[..]) | Text | Flags
    pub default: DefaultSrc,          // Builtin(..) | ModelDerived(fn) — что делает build_args сегодня
    pub applies: Applies,             // All | Nextn | ExternalDraft | Moe | Vision | Ssm
    pub argv: Argv,                   // Flag("-c") | Repeat | LocalOnly | None
    /// вклад в VRAM: байт на токен контекста (0 если не влияет)
    pub vram_per_token: fn(&ModelCaps) -> f64,
}

knobs! {
    ctx          : u32,  "context size",   Group::Context, Num{..}, Builtin(131072), All,          Flag("-c"), kv_main;
    ctk          : KvType,"KV cache K",    Group::Context, Enum(KV_TYPES), Builtin("q8_0"), All,   Flag("--cache-type-k"), 0.0;
    ckv_draft    : KvType,"draft KV type", Group::Speed,   Enum(KV_TYPES), ModelDerived(..), Nextn, Flag("-ctkd"), 0.0;
    draft_tokens : u16,  "draft tokens",   Group::Speed,   Num{1,8},      ModelDerived(..), Nextn,  Flag("--spec-draft-n-max"), 0.0;
    ncmoe        : u16,  "experts on CPU", Group::Memory,  Num{..},       Builtin(58), Moe,         Flag("--n-cpu-moe"), 0.0;
    cache_reuse  : u16,  "cache reuse",    Group::Speed,   Num{..},       Builtin(256), NotSsm,    Flag("--cache-reuse"), 0.0;
    // ...
}
```

Три вещи, которые это даёт сразу:

1. **Добавить настройку = добавить строку.** Не 8 правок.
2. **Релевантность.** `applies` решает, показывать ли knob: `ncmoe` — только MoE,
   `draft_*` — только при MTP/внешнем драфте, `mmproj` — только при `vision`,
   `cache_reuse` — не для гибридных SSM. Никаких «20 полей, половина мертва».
3. **`default` — исполняемый.** Не строка в документации, а функция, которую вызывает
   `build_args`, если значение не задано. Дефолт перестаёт быть «магией в коде» и
   становится виден в UI как `default` с пометкой источника.

Killer-тест безопасности рефакторинга: `tests/argv_golden.rs` — для каждой из 6 моделей
снять текущий `--dry-run` в файл и требовать побайтового совпадения после каждого шага.
Миграция не должна менять ни одного аргумента, пока мы сами этого не захотим.

## 4. Слой 2: происхождение значения (`src/resolve.rs`)

Вместо плоского `Cfg`:

```rust
pub enum Source { Cli, Model, Defaults, Builtin }

pub struct Resolved {
    ctx: Val<u32>, ctk: Val<String>, /* ... */
}
pub struct Val<T> { pub v: T, pub from: Source }
```

Три профиля остаются как есть (это дёшево и предсказуемо), а `Source` вычисляется при
разрешении — копии нет, дрейфа нет.

Что это даёт в UI и CLI:

```
 context size      262144   model     ← взято из [model."Ornith-1.5-9B-Q6_K"]
 KV cache K        q8_0     default
 cache reuse       0        builtin   ← авто-выключен: гибридный SSM
 flags (extra)     (none)   model
```

`localmodel run X --dry-run --explain` печатает ту же таблицу в stdout — это ответ на
«почему в команде этот флаг» без чтения исходников. Каждый токен argv можно покрасить
по источнику, тогда `d` в хабе показывает не просто команду, а её происхождение.

## 5. Слой 3: калькулятор VRAM для GGUF (`fit::for_gguf`)

Сейчас `fit.rs` умеет только каталог Strata по опубликованным таблицам. Для хаба нужен
честный расчёт по метаданным самого файла — они у нас уже читаются в `gguf.rs`.

```
vram ≈ weights            (file_size × 1.01)
     + kv_main            (n_ctx × Σ_attn_layers n_kv_heads × (k_len+v_len) × bpe(ctk,ctv))
     + kv_draft           (n_ctx × n_nextn_layers × ... × bpe(ctkd,ctvd))   // только spec-mtp
     + compute            (~0.9–1.3 GiB, калибровка по ubatch/ctx)
     + cuda_ctx           (~0.3 GiB)
```

`bpe`: f16/bf16 = 2.0, q8_0 = 1.0625, q6_k = 0.820, q5_1 = 0.75, q5_0 = 0.6875,
q4_1 = 0.625, q4_0/iq4_nl = 0.5625.

Проверка на сегодняшнем замере: Ornith Q6_K, 9 attention-слоёв × 4 головы × 512,
262144 токена, q8_0 → **4.78 GiB** KV; + 7.04 GiB весов = 11.8; фактические 13.7 GiB
(14009 MiB) ⇒ накладные ~1.9 GiB (compute + draft-ctx + CUDA). Сходится, значит формулу
можно калибровать по 3–4 точкам (Ornith n-max 2/3, Qwen3.8, Nemotron) и держать
поправочные константы в одном месте с комментарием «измерено такого-то числа».

Две функции поверх:

- `Estimate::verdict()` → `fits / tight (<1 GiB запаса) / no` (переиспользуем `fit::Verdict`).
- `suggest_ctx(meta, hw, kv)` → максимальный ctx, который влезает, с округлением
  к 2^n (32768, 65536, 131072, 196608, 262144). Инверсия той же формулы:
  `ctx_max = (room − weights − overhead) / kv_bytes_per_token`.

Это превращает подбор из «поставил, поймал OOM, уменьшил» в арифметику до запуска.
Заодно в хабе появляется строка «максимум для этой карты: 262144» и кнопка «поставить максимум».

## 6. `localmodel hub` — экран

```
┌ models ──────────────────┐┌ Ornith-1.5-9B-Q6_K ─────────────────────────────┐
│ ● Ornith-1.5-9B-Q6_K     ││ 7.0G Q6_K · 33L · MTP · qwen35 · dense           │
│   Ornith-1.5-9B-AD-Q8_0  ││ VRAM 13.7 / 15.5 GB  ████████████░░  fits        │
│   Qwen3.8-27B-GSQ-...    ││ ctx max для этой карты: 262144                   │
│   Nemotron-3.5-74B       ││                                                  │
│                          ││ CONTEXT                                          │
│ + добавить с HuggingFace ││  context size        262144    model             │
│                          ││  KV cache K          q8_0      default           │
│                          ││  KV cache V          q8_0      default           │
│                          ││ SPEED                                            │
│                          ││  draft tokens        2         model             │
│                          ││  draft KV type       q8_0      builtin           │
│                          ││  cache reuse         off       builtin (SSM)     │
│                          ││ SERVER                                           │
│                          ││  port                auto      builtin           │
│                          ││ ── help ────────────────────────────────────────  │
│                          ││ Размер окна в токенах. KV растёт линейно: для    │
│                          ││ этой модели 262144 токена q8_0 ≈ 4.8 GiB.        │
└──────────────────────────┘└──────────────────────────────────────────────────┘
 ↑↓ выбор · ⇥ панель · Enter править · Tab цикл · − сбросить · d argv · L запуск · s сохранить · x удалить
```

Поведение:

- **Список моделей**: скачанные + `+ добавить с HuggingFace` + установленные Strata-паки.
  Бейджи: `● running`, `+mtp`, `+draft`, `MoE`, размер, квант.
- **Панель настроек**: только релевантные knobs, сгруппированные; справа — эффективное
  значение и источник. `Enter` — инлайн-ввод с валидацией по `Kind` (числа с min/max,
  enum по `Tab`, путь с автодополнением по `models/`). `−` снимает override.
- **Живой прогноз** внизу: VRAM, вердикт, `ctx max`. Пересчёт на каждое изменение — это
  дёшево, вся математика из §5 в памяти.
- **`d`** — панель argv с раскраской по источнику (как `--dry-run --explain`).
- **`s`** — пишет в `settings.toml` **только изменённые ключи**, не снимок всего.
- **`L`** — запуск. Модель уже настроена, отдельного шага «а теперь введи команду» нет.
- **`x`** — удалить `.gguf` (с подтверждением и показом, сколько освободится).
- Без TTY (`localmodel hub` в pipe) — печатает список и выходит с кодом 0; вся логика
  остаётся доступна через `settings --show/--set` и `run --dry-run`.

Экран живёт в `src/hub.rs` и переиспользует `boxed`/`section`/цвета/`screen_size`.
`View`-машина состояния копируется с dashboard (`main.rs:3151-3210`), но без запущенного
сервера: хаб нужен *до* запуска.

## 7. Поток «даю ссылку с HF → получаю настроенную модель»

`localmodel add` сегодня — обёртка над `curl` с угадыванием имени файла (`download.rs`).
Целевой поток:

### 7.1 Разбор ссылки

| Вход | Что делаем |
|---|---|
| `.../resolve/main/<file>.gguf` | качаем напрямую |
| `.../blob/main/<file>.gguf` | переписываем на `resolve` |
| `https://huggingface.co/<repo>` | `GET /api/models/<repo>` → дерево файлов → выбор из `.gguf` |
| `hf.co/<repo>/<file>` | короткая форма, то же |
| `.../tree/main/<dir>` | список `.gguf` в этой папке |

В выборе файлов показываем размер и квант, сортируем по «разумности» для этой карты
(Q6_K → Q5_K_M → Q4_K_M → Q8_0) и сразу рисуем вердикт `fits/tight/no` из §5 —
до скачивания, по размеру из API.

### 7.2 Догрузка сопутствующего

- **Шарды** `*-00001-of-000NN.gguf`: качаем все части, `scan()`/`find_draft()` учатся
  считать набор одним файлом (сейчас каждый шард стал бы отдельной «моделью»).
- **`mmproj-*.gguf`**: если в репозитории есть и в карточке заявлено vision — тянем рядом,
  в профиль пишем `mmproj = "..."`, `vision = true`.
- **`generation_config.json`**: если есть — берём `temperature`/`top_p` как рекомендацию
  (показываем как «из карточки», не применяем молча).

### 7.3 Валидация после скачивания

GGUF-магия, заголовок парсится, размер совпал с `Content-Length`, `block_count` > 0.
Не сошлось — `.part` удаляем, внятная ошибка. Сейчас не проверяется ничего: битый файл
просто появится в списке и упадёт при запуске.

### 7.4 Авто-профиль (`src/suggest.rs`, чистая функция)

`suggest(meta, hardware, prefs) -> Profile` — без запуска и без GPU, поэтому тестируется
юнит-тестами:

```
ctx           = min(model.context_length, suggest_ctx(...))          // §5
ctk / ctv     = q8_0, если влезает; иначе q4_0 + предупреждение о качестве
ctkd / ctvd   = q8_0                                                 // замер: бесплатно
draft_tokens  = 3 при nextn; 1 при внешнем MTP; 7 для draft-dflash
ncmoe         = из размеров файла и свободной VRAM (MoE)
cache_reuse   = выключен, если ssm_layers > 0                         // сегодняшний warning
ngl           = 99; flash_attn = on; host = 127.0.0.1
```

И главное — **объяснение**: после сохранения печатается, *почему* так.

```
Ornith-1.5-9B-Q6_K
  ctx        262144   максимум модели, влезает: 7.0 веса + 4.8 KV + 1.9 накладные = 13.7 из 15.5 GiB
  KV         q8_0/q8_0
  MTP        включён (blk.32.nextn), draft 3 токена
  сохранено  [model."Ornith-1.5-9B-Q6_K"]  (5 ключей, не 20)
```

Флаги: `--launch` (сразу запустить), `--yes` (без вопросов), `--print` (показать профиль,
не писать), `--no-suggest` (ничего не настраивать).

## 8. Гигиена файла настроек

1. **`toml_edit` вместо `toml::to_string_pretty`.** Сохраняем комментарии, порядок и
   форматирование; меняем только тронутые ключи. Сейчас `save()` перезаписывает всё.
2. **`schema_version = 1`** в шапке + миграции при загрузке.
3. **Ошибки per-table.** `deny_unknown_fields` на всём файле означает «одна опечатка —
   все профили отключены». Нужно: разобрать через `toml_edit`, неизвестные ключи и битые
   значения собрать в список и показать в хабе красными строками, остальное применить.
4. **`localmodel settings --show --origin`** — та же таблица с происхождением, без TUI.
5. **`--set ctx=131072 --set ctk=q8_0 --unset extra --edit`** — паритет с хабом для скриптов.
6. **Один файл.** После рефакторинга `settings.toml` — единственное место, где что-то
   хранится; `hub`, `add --launch`, dashboard «save» и `settings --set` пишут в него
   через один и тот же `settings::patch(keys)`.

## 9. `extra`: оставить, но приручить

Свободные флаги нужны — llama.cpp добавляет их быстрее, чем мы успеваем заводить knobs.
Но они не должны быть невидимыми:

- **Валидация по бинарю**: кэшируем `llama-server --help` в `~/.cache/localmodel/help-<mtime>.txt`,
  проверяем каждый флаг из `extra` и из argv. Неизвестный — предупреждение в хабе,
  `--strict` → ошибка. (Ровно этот класс ошибок ловит `unknown argument: -kvod` из
  `docs/BACKEND.md`.)
- **Обнаружение затенения**: `-ctkd q4_0` в `extra` при `ctkd = "q8_0"` в профиле — показываем
  «перекрыто extra», а не молчим.
- **`promote to knob`**: в хабе `Enter` на строке extra предлагает разложить известные флаги
  по типизированным полям.
- `has_flag()`-эвристики в `build_args` удаляются: argv собирается из реестра, `extra`
  добавляется последним и проверяется на конфликты явно.

**Отклонение от исходного плана (фаза 0).** `build_args` остался прежним: таблица
пока владеет *описанием* полей, а не сборкой argv. Причина — перенос `build_args` на
реестр требует provenance и generic-рендера, то есть работы фазы 3, и без них это была
бы переделка ради переделки. argv-контракт зафиксирован golden-тестами, поэтому
переписать его в фазе 3 безопасно.

Порядок не случайный: 0 и 1 не видны пользователю, но именно они делают 3 и 4 короткими.
Если делать хаб первым — он будет пятым местом, где перечислены поля.

Тесты, которые стоит завести по ходу:

- `argv_golden`: 6 моделей × argv до/после — побайтовое равенство.
- `kv_math`: Ornith 262144/q8_0 → 4.78 GiB ±2 %.
- `suggest`: для 4 реальных GGUF — ожидаемые ctx/KV/draft.
- `topology`: `applies` скрывает `ncmoe` у dense, `draft_*` без MTP, `mmproj` без vision.
- `settings_roundtrip`: правка одного ключа сохраняет комментарии, порядок и остальные профили.

## 11. Что нужно решить до старта

1. **Макрос или map.** `macro_rules!` + типизированная структура (быстрее, но макрос
   на ~150 строк) против `BTreeMap<String, Value>` + типизированные геттеры (проще,
   но проверки значений уезжают в рантайм). Рекомендую макрос: компилятор продолжит
   ловить опечатки в `build_args`.
2. **Судьба `localmodel settings`.** Рекомендую оставить только `--show/--set/--unset/--edit`
   и удалить интерактивный `dialoguer`-цикл: его роль целиком забирает хаб.
3. **Источник дефолтов.** Оставляем «дом в коде» (`Builtin`) и показываем в UI как
   `default`, или переносим в `settings.toml` как `[defaults]` при первом запуске?
   Рекомендую первое: файл остаётся маленьким и содержит только то, что пользователь
   действительно менял.
